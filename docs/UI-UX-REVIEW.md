# Slides Thief 网页端 UI / 交互问题清单

审查对象：`site/` 下的 React 网页应用（v2.3.0）
审查方式：通读 `site/app/` 全部组件与 hooks、`globals.css`、`i18n.ts`，并在本地 `npm run dev` 实际运行、导入图片、执行自动校正后逐项核对。
说明：本文只列问题与改进建议，未做任何代码修改。

---

## 优先级总览

| 级别 | 含义 | 条目 |
| --- | --- | --- |
| P0 | 会导致用户丢失工作成果、或让人看不懂/用不了的问题 | 1–6 |
| P1 | 明显拖慢主流程、造成困惑或不一致的问题 | 7–22 |
| P2 | 打磨项：一致性、可访问性、文案、信任感 | 23–37 |

## P0 — 数据丢失与流程阻断

### 1. 二次选择文件会静默清空已有的全部图片

`site/app/hooks/useImportPipeline.ts` 里 `loadFiles()` 直接 `setSlides(nextSlides)`，同时 `revokeSlideObjectUrls()` 把旧图片的 Blob URL 全部释放。也就是说，用户已经手工调好 30 张照片的角点后，只要再点一次上传区想"补两张"，前面的工作就全部消失，没有确认、没有提示，撤销栈里也没有这一步（`pushHistory()` 未被调用，所以 Cmd+Z 救不回来）。

**建议**
- 默认行为改为「追加」：新文件按文件名归并到现有列表尾部，重复文件名给出提示。
- 如果确实要保留「替换」语义，必须先弹确认框，并且在替换前 `pushHistory()`，让 Cmd+Z 可以恢复。
- 上传区文案区分两种状态：空列表时显示"点击或拖拽上传"，已有图片时显示"添加更多照片"。

### 2. 任何设置改动都会让已生成的 PDF 下载链接凭空消失

`clearExport()` 被挂在 `updateSettings`、`deleteSlide`、`handleUndo/Redo`、角点拖动等几乎所有操作上（`site/app/hooks/usePreferences.ts:27`、`useSlideDeck.ts`、`useQuadEditor.ts:80`）。用户生成完 PDF 后，只要顺手调一下"输出效果"或碰了一下角点，"下载 PDF"链接就无声地消失了，很容易被理解成"出 bug 了"。

**建议**
- 不要直接移除链接，而是把它置为"已过期"状态：保留按钮但变灰，旁边提示"设置已更改，请重新生成"。
- 或者把生成与下载合并为一个动作（见第 8 条）。

### 3. 删除图片无确认、也没有可见的撤销入口

`SlideSidebar` 里每行的删除按钮直接调用 `deleteSlide(slide.id)`；全局快捷键里 `Delete` / `Backspace` 也会直接删掉当前选中项（`site/app/keyboard-shortcuts.ts:62`）。撤销功能其实存在，但唯一的发现路径是"关于"弹窗里的快捷键表。

**建议**
- 删除后在状态区出现一条可点击的「已删除 xxx ・ 撤销」提示（Toast/Snackbar），停留数秒。
- 或在工具栏放出常驻的撤销 / 重做按钮，让 `handleUndo`、`handleRedo` 有可见入口，而不只是快捷键。

### 4. 处理过程中仍可删除图片，与其他按钮的禁用逻辑不一致

`busy` 为真时，自动校正、生成 PDF、导入/导出角点、清空全部、上传区全部 `disabled`，唯独每行的删除按钮没有 `disabled`（`site/app/components/SlideSidebar.tsx:361-369`）。实测在检测进行中，删除按钮依然可点。

**建议**：让删除按钮遵循同一套 `busy` 规则，或者显式允许删除并保证删除后正在进行的检测任务被正确取消。

### 5. 移动端设置面板里的输入框会触发 iOS Safari 自动放大

`globals.css:1940` 在移动/粗指针断点下把 `select` 和 `input` 的字号设为 `--font-size-lg`（16px），这是防止 iOS 聚焦时页面放大的标准做法，且 `DESIGN.md` 明确写了"Mobile: Inputs remain at least 44px high and use 16px text to avoid mobile browser zoom"。但紧接着 `globals.css:1948-1958` 又用更高优先级的 `.settings select`、`.settings input`、`.morePanel input` 把字号覆盖回 `--font-size-md`（13px）。

结果就是：设置菜单里的"目标文件名""宽度""导出质量"等输入框，在 iPhone 上一点就会整页放大，且不会自动缩回。这是整个应用在手机上最常触碰的一组控件。

**建议**：移动端断点下，凡是 `input` / `select` 的字号都不低于 16px；如果视觉上嫌大，用 `transform: scale()` 或调整控件尺寸，而不是调 `font-size`。

### 6. 检测结果标了"建议复查"，却不说为什么

检测管线已经算出了具体原因（`site/app/detection/detect.ts:91-111`：`low_confidence`、`weak_edge_support`、`ambiguous_candidates`、`fallback_used`），一路通过 worker 传进了 `SlideItem.reviewReasons`，但全局搜索表明它在任何 UI 组件里都没有被渲染过。用户看到的只有一个感叹号和"建议复查"，不知道是边缘太糊、候选框冲突，还是压根没检测到、用了兜底框。

**建议**
- 在详情面板把 `reviewReasons` 翻译成人话展示，例如"幻灯片边缘对比度不足，请确认四角位置"。
- 缩略图徽章的 `title` 里也带上原因，鼠标悬停即可看到。
- `fallback_used`（完全没检测到）和 `low_confidence`（检测到但不确定）应该用不同的视觉等级，前者几乎肯定需要人工介入。

## P1 — 主流程效率与一致性

### 7. 只有侧栏的上传框能接收拖拽，画布区不能

`onDragOver` / `onDrop` 只绑定在 `.dropzone` 这一个按钮上（`site/app/components/SlideSidebar.tsx:287-298`），窗口级别没有任何拖放监听。用户很自然地会把照片拖到中间那块大画布上——什么都不会发生，文件还可能被浏览器直接打开，当前会话全丢。

**建议**
- 在 `window` 上监听 `dragover` / `drop`，拖入时整页显示一层覆盖提示，任意位置松手都能导入。
- 同时在 `window` 上监听 `paste`，支持从截图工具直接 Ctrl+V 粘贴图片。

### 8. "生成 PDF"和"下载 PDF"被拆成了两步

当前流程是：点"生成 PDF" → 等待 → 侧栏状态区出现一个"下载 PDF"文字链接 → 再点一次。这个链接混在状态文字旁边，视觉权重比刚才点过的主按钮低得多，实测很容易漏看，而且它随时可能因为第 2 条的原因消失。

**建议**
- 生成完成后直接触发下载，把主按钮变成"重新生成"。
- 若要保留手动下载（方便重复保存），就把它升级为主按钮位置的实体按钮，并明确显示文件名和体积（`ExportArtifact` 里已经有 `filename` 和 `byteLength`，目前没用上）。

### 9. 自动校正没有进度和取消

导出有 `x/y` 进度文字和"取消"按钮（`useExportWorker.ts:36-41`、`SlideSidebar.tsx:215-225`），但检测只有一行"校正中: 文件名"，没有"第几张/共几张"，也没有取消按钮。批量导入几十张照片时，用户完全不知道还要等多久，中途改主意也停不下来（`cancelDetection` 其实已经实现，只是没有 UI 入口）。

**建议**：复用导出那套进度文案格式，加上进度条和取消按钮；缩略图列表里也用进度态区分"已完成/处理中/排队中"。

### 10. 关键导出参数被埋在"设置 → 更多设置"两层折叠里

"PDF 页面""纸张规格""宽度""高度""导出质量""输出效果""填充色"全在 `<details class="moreSettings">` 内部（`site/app/components/Header.tsx:90-116`）。而"输出效果"（原图/清晰增强/高对比/黑白扫描）是对成品观感影响最大的开关之一，现在要点两次才能看见。

**建议**
- 把"输出效果"提到一级设置，或者做成画布上的实时预览切换（四个缩略预览直接点选）。
- 其余参数按"页面"和"画质"分组，用带标题的分区代替一个笼统的"更多设置"。

### 11. 桌面端"设置"折叠面板无法收起

`Header.tsx:69-77` 的 `onToggle` 在非移动断点下强制 `event.currentTarget.open = true`。也就是说桌面端这个 `<summary>` 看起来可以点，点了却没有任何反应。一个看似可交互却永远无响应的控件是典型的反模式。

**建议**：桌面端要么把它渲染成普通容器（不给 `<summary>` 这种"可点击"的外观），要么真的允许收起以换取更宽的顶栏空间。

### 12. 不能调整页面顺序

PDF 的页序完全由导入时的 `a.name.localeCompare(b.name, undefined, {numeric: true})` 决定（`useImportPipeline.ts:67`）。手机连拍的文件名未必与讲演顺序一致，混合来源（微信保存 + 相机原图）时更是必然错乱，而用户对此毫无办法，只能退出去改文件名重来。

**建议**：缩略图列表支持拖拽排序，或至少提供"上移/下移"按钮；顺序变化时同步更新页码编号。

### 13. 没有批量操作

每张照片的角点只能一张张调。会议室场景里，同一场演讲的所有照片往往是同一机位、同一角度，第一张调好之后理应能复用。

**建议**
- 提供"把当前页角点应用到全部/后续页"。
- 提供"批量重新检测所选页"，而不是只有"重置本页"和"全部重跑"两个极端。

### 14. "导出 JPG"藏在一个只有一项的下拉菜单里

拆分按钮右侧的箭头展开后，菜单里只有"导出 JPG 图片"一项（`SlideSidebar.tsx:142-176`）。为一个选项付出「发现下拉 → 展开 → 阅读 → 点击」的代价并不划算，而对于只拍了一两张的用户，导出 JPG 反而是更常见的需求。

**建议**：并排放两个按钮（"生成 PDF" / "导出图片"），或者在设置里让用户指定默认导出格式，主按钮跟着变。

### 15. 状态区一行文字承担了太多角色

`statusText`（`SlidesThiefApp.tsx:333-343`）按优先级复用同一行显示：错误 > 忙碌 > 待上传 > 校正中 > 生成中 > 已生成 > 复查提示。副作用是错误信息会被下一次操作的状态文字覆盖掉，用户来不及看清；而且错误没有关闭按钮，也没有"重试"入口。

**建议**：把瞬时进度（状态行）和需要用户处理的错误（可关闭的警示条，带重试/查看详情）分离成两个区域。

### 16. 所有 worker 错误文案是硬编码英文

九种语言的界面下，worker 层抛出的文案一律是英文，例如 `"The image worker returned an invalid response."`（`useDetectionWorker.ts:92`）、`"The export worker stopped unexpectedly."`（`useExportWorker.ts:98`）。角点导入的报错同样是写死的英文（`SlidesThiefApp.tsx:253-274`，如 `"Import images before importing corner coordinates."`）。

**建议**：把这些字符串收进 `i18n.ts`，用错误码而非英文原文在模块间传递。

### 17. 原生 `window.confirm` 与整体设计语言割裂

清空全部（`useSlideDeck.ts:71`）和"有 N 张建议复查，仍要生成 PDF 吗？"（`SlidesThiefApp.tsx:533`）都用了浏览器原生确认框。它无法套用项目的设计令牌，在移动端表现尤其突兀，按钮文案固定为"确定/取消"而无法写成"仍然生成/先去复查"这种有信息量的动词。

**建议**：项目里已经有 `ModalShell` 组件，复用它做一个确认对话框，按钮文案写明后果。

### 18. 复查确认对话框把用户推到了一个死胡同

点"取消"后，代码会把选中项跳到第一张待复查的照片（`confirmExportReady`），但用户此时并不知道"接下来要看哪几张""看完怎么继续"。多张待复查时没有"下一张待复查"的导航。

**建议**：进入一个轻量的"复查模式"：只在待复查的页之间跳转，每页给出"确认无误"按钮，全部确认后自动回到导出。

### 19. "重置本页"的行为不可预测

`resetSelected()`（`useQuadEditor.ts:268-290`）有两种完全不同的分支：如果存在 `autoDetection` 快照就瞬间还原；否则重新跑一次检测（耗时且可能得到不同结果）。按钮文案一样，用户无法预知会发生哪种。

**建议**：拆成两个含义明确的动作——"还原自动检测结果"和"重新检测本页"，后者禁用时给出原因。

### 20. 详情面板信息密度低，还混进了一条营销文案

详情面板固定占据桌面端 320px，里面是七行 `metrics`（文件、状态、尺寸、比例、方法、置信度、隐私）加四行角点坐标。其中"隐私：浏览器本地处理"是一条恒定不变的静态文案，却被排版成"每页数据"的样式（`SlidesThiefApp.tsx:610`）；"置信度"给出一个用户无法据此行动的数字；角点坐标是只读的，不能直接输入修改。

**建议**
- 把隐私说明移到页脚或"关于"弹窗，不要占用数据位。
- 把置信度换成"建议复查/看起来不错"这类可行动的结论，数字放进 tooltip。
- 角点坐标改成可编辑的输入框，这样详情面板才真的有存在价值。

### 21. 画布缺少滚轮缩放和拖拽平移

全局搜索确认没有任何 `wheel` / `pinch` / 手势监听。放大只能点 ± 按钮，每次固定 1.18 倍；放大后要移动视野只能靠外层容器的滚动条。精修角点本来就是个需要频繁「放大—平移—微调」的操作，当前的交互成本偏高。

**建议**：支持滚轮/触控板缩放（以光标为锚点）、空格或中键拖拽平移、双指缩放；拖动角点到画布边缘时自动滚动。

### 22. 放大镜固定在手柄正上方，靠近顶边时会被裁掉

`.loupeOverlay` 用 `transform: translate(-50%, -100%)` 加负的上外边距把放大镜钉在手柄上方（`globals.css:2245-2258`）。而 1 号和 2 号角点恰恰位于图片顶部——最需要放大镜的时候，它正好越出画布容器。

**建议**：根据手柄在视口中的位置自动翻转到下方/侧方，并把放大镜限制在画布可视区域内。

## P2 — 一致性、可访问性、信任感

### 23. 画布上的四边形用了品牌色，违反项目自己的设计规范

`DESIGN.md` 写得很明确：`Teal Precision` 用于"active quad boundary"，并在 Don'ts 里写了"Don't use terracotta for ordinary canvas geometry"。但 `useCanvasViewport.ts:100` 实际画的是 `rgba(200, 69, 53, .98)`，正是 terracotta `#C84535`。

同时画布里的颜色全部硬编码（`:86` 的 `rgba(255,255,255,.36)` 图片描边、`:112` 的手柄描边、`:118` 的 `#172026` 数字），不走 CSS 变量，因此不随明暗主题变化——白色描边在浅色主题的浅色背景上几乎看不见。

**建议**：通过 `getComputedStyle` 读取主题令牌后再绘制，并把四边形改回 teal，让红色专门留给"需要注意/危险"。

### 24. 幻灯片列表用 `aria-pressed` 模拟选中态

每一行是一个带 `aria-pressed` 的按钮外加一个 `<li>`（`SlideSidebar.tsx:310-320`）。实测无障碍树里同一条目出现两次（一次 listitem，一次 toggle button），屏幕阅读器会读成"按下/未按下"的开关，而不是"第 3 项，共 12 项，已选中"。

**建议**：改用 `role="listbox"` + `role="option"` + `aria-selected`，或保留列表语义并用 `aria-current="true"` 标记当前页。

### 25. 方向开关的无障碍名称会随状态变化

`Switch` 的可访问名取自 `label`，而调用方传入的是 `orientation === "portrait" ? "纵向" : "横向"`（`SourceFormatControls.tsx:115`）。于是屏幕阅读器读到的是"纵向，开关，已选中"，无法得知这个开关控制的是什么。

**建议**：`aria-label` 固定为"方向"，把当前值通过 `aria-checked` 或独立的状态文本表达。

### 26. `<html lang>` 首屏写死为 `en`

`layout.tsx:55` 硬编码 `<html lang="en">`，运行时才由 `usePreferences` 改成实际语言。SSR 首屏和禁用 JS 的场景下，中文/日文内容会被声明成英文，影响屏幕阅读器发音和搜索引擎语言判定。

**建议**：服务端渲染时根据 `Accept-Language` 或路由段输出正确的 `lang`。

### 27. 语言、主题、导出设置全部不持久化

全仓库搜索 `localStorage` / `sessionStorage` / `indexedDB` 零命中。每次刷新，主题回到"自动"、语言回到浏览器检测值（会覆盖用户上次的手动选择）、宽度/质量/输出效果/目标文件名全部重置为默认。对于会反复使用的批处理工具，这个代价不小。

**建议**：把偏好写入 `localStorage`，并明确区分"用户显式选择"和"自动检测"——前者不应被 `detectBrowserLocale()` 覆盖。

### 28. 刷新页面即丢失全部工作，且没有任何警告

调好角点的几十张照片只存在于内存里，误触刷新、切后台被回收、手机来电，全部归零。

**建议**：至少在有未导出的工作时注册 `beforeunload` 提示；进一步可以把角点数据和文件句柄放进 IndexedDB，支持"恢复上次会话"。

### 29. 无条件加载 GA4，与"关于"弹窗里的隐私承诺存在张力

`layout.tsx:72-84` 在所有地区、所有用户上无条件注入 `gtag.js`，`trackEvent` 会上报导入张数、是否含 HEIF、导出体积、错误信息等（`lib/types.ts:10`）。而"关于"弹窗写的是"照片和 PDF 均在本地处理，绝对不会上传到任何服务器"。照片本身确实没上传，这点没问题，但"绝对不会上传到任何服务器"这句话与实际存在的匿名遥测放在一起，容易被理解为过度承诺。界面支持德/法/西/葡语，也意味着相当比例的用户在 GDPR 管辖范围内，而目前既没有同意提示也没有退出开关。

**建议**：把承诺精确化为"您的照片不会离开本机"，并在"关于"里说明收集哪些匿名使用数据、提供一个关闭开关；欧盟地区考虑加载前先征得同意。

### 30. 页脚语义与视觉位置不符，且移动端被整块隐藏

主题/语言/关于这组控件包在 `<footer class="prefsBar">` 里（`SlidesThiefApp.tsx:717`），但 CSS 把它放在了右上角（`grid-area: prefs`）。移动端又直接 `display: none`（`globals.css:1525-1527`），功能靠 `PreferencesControls` 在设置菜单里再渲染一份来补。同一组控件存在两处实现，容易在后续维护中走样。

**建议**：语义上用 `<div>` 或 `<nav>`，位置交给布局决定；两处渲染保持单一数据源和一致的排列顺序。

### 31. 移动端隐藏了当前文件名和上下页按钮

`globals.css:1849-1853` 在窄屏下隐藏了 `.reviewPrevious`、`.reviewNext` 和 `.reviewBar .title`。用户在手机上编辑角点时，画布上方看不到当前编辑的是哪张、第几张，只能回头去看横向缩略图条上哪个是高亮的。

**建议**：至少保留"03 / 12"这样的页码指示；上下页按钮可以移到画布左右两侧做成半透明浮层。

### 32. 文件名截断后在触屏上无法查看全名

`displayFileName(slide.name, isMobile)` 做了截断，完整名放在 `title` 属性里（`SlideSidebar.tsx:336-338`）——而 `title` 依赖鼠标悬停，触屏用户永远看不到。多张来自同一目录、前缀相同的照片（`IMG_5995`、`IMG_5996`…）截断后可能完全无法区分。

**建议**：中间省略（保留头尾）而非尾部截断；或在详情面板展示完整文件名（现在详情面板的"文件"行也用的是完整值，但移动端详情面板默认折叠）。

### 33. iOS 上的下载路径没有任何说明

检测到 iOS 时代码会去掉 `download` 属性，改为 `target="_blank"` 打开（`SlideSidebar.tsx:232`）——这是绕开 Safari 限制的正确做法，但用户看到的是 PDF 在新标签页里打开，不知道还要点分享菜单里的"存储到文件"。

**建议**：iOS 下把链接文案改为"打开 PDF"，并附一行"在打开的页面点击分享 → 存储到文件"。

### 34. 空状态只有一句话，缺少引导

画布空态是纯文字"上传图片后点击自动校正按钮"（`i18n.ts:341`），侧栏空态是一个虚线框。新用户既不知道"什么样的照片效果好"，也不知道四角手柄长什么样、怎么拖。

**建议**：空状态里放一张示意图（倾斜照片 → 四角框 → 校正结果），或提供一张内置示例照片让用户一键试跑。README 的「Tips」里那些拍摄建议（边界要可见、避免手和人头遮挡）也值得搬到界面上。

### 35. 快捷键只能在"关于"弹窗里发现

J/K 翻页、方向键微调、Shift 加速、Cmd+Enter 导出这些设计得不错的快捷键，唯一的曝光位置是"关于"弹窗（`AboutModal.tsx:47-90`）——而"关于"按钮通常没人会点。只有"生成 PDF"按钮的 `title` 里带了快捷键提示。

**建议**：加一个 `?` 唤起的快捷键面板（这是同类工具的通用约定），并在相关按钮的 `title` 里统一标注快捷键。

### 36. 计数文案用字符串拼接实现复数，i18n 上比较脆弱

状态行是 `${slides.length} ${text.waiting}`，于是中文词条被写成 `"张，等待校正"`、日文写成 `"枚、補正待ち"`、英文写成 `"images, waiting to straighten"`（`i18n.ts:343` 等）。这种把量词/助词切开的写法一旦要处理英文单复数或俄语那种多形式复数就会崩，而且译者拿到孤立的 `"张，等待校正"` 很难理解上下文。

**建议**：统一改成接收 `count` 的函数式词条（`reviewSummary` 已经是这么做的），内部用 `Intl.PluralRules`。

### 37. 文件名输入框会静默吞掉字符

`sanitizePdfBaseName` 在每次按键时剥离非法字符和 `.pdf` 后缀（`Header.tsx:122`），用户输入 `报告:第一场` 会发现冒号凭空消失，却不知道为什么。另外输入框清空后，实际导出会回落到 `flattened_slides.pdf`（`filename.ts:14`），但界面上不会显示这个兜底名。

**建议**：允许输入后再校验，在字段下方给出"文件名不能包含 : / \\ 等字符"的提示；输入为空时把 `flattened_slides` 作为 placeholder 显示出来。

---

## 建议的推进顺序

1. **先堵数据丢失**：第 1、2、3 条。这三条是用户真的会"白干一场"的场景，改动量都不大。
2. **再补移动端**：第 5、31、32、33 条。手机拍照、手机处理是这个产品最自然的使用链路，而目前手机体验的短板最明显。
3. **然后是流程效率**：第 7、8、9、12、13 条，把"导入 → 校正 → 复查 → 导出"这条主路径拉顺。
4. **最后做一致性打磨**：第 23 条（画布配色回到设计规范）、第 24/25/26 条（无障碍语义）、第 27/28 条（持久化）。

第 29 条（隐私文案与遥测）建议单独决策，因为它涉及产品定位和合规判断，不是纯技术改动。
