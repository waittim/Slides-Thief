下面这份计划适合直接交给 coding agent 执行。核心原则是：**先重构检测接口与评测体系，再逐步替换内部算法；每个阶段都必须可单独测试、回滚和对比。**

当前网页端在 `detectFiles()` 中把输出比例直接传入 `detectQuad()`，检测器仅依次尝试 `contrast-lines → fallback-frame`；CLI 则额外包含 `mask-lines`。
现有测试主要覆盖比例解析、透视变换、增强和点排序，尚未形成四角检测回归集。

## 3.3 核心指标

### Normalized Corner Error

每个角点误差除以图片对角线：

```text
corner_error =
distance(predicted, ground_truth)
÷ image_diagonal
```

重点记录：

* 平均角点误差；
* 最大角点误差；
* 四个角都低于 1% 的图片比例；
* 四个角都低于 2% 的图片比例。

### Quad IoU

把预测四边形和标注四边形转成 mask，计算：

```text
intersection / union
```

### 高置信度错误率

这是最重要的安全指标：

```text
confidence ≥ 0.8
但 Quad IoU < 0.75
```

此比例必须尽可能接近零。

## 3.4 建立当前基线

在修改任何算法之前，保存：

```text
benchmark-baseline.json
```

之后每个 PR 都需要输出：

```text
benchmark-current.json
benchmark-diff.md
```

## P0-2：将 CLI 的 mask-lines 移植到网页端

### 不要作为 fallback 移植

错误方式：

```text
contrast-lines 失败
→ 才执行 mask-lines
```

正确方式：

```text
contrast-lines 始终生成候选

```

### 创建

```text
site/app/detection/mask-lines.ts
```

移植内容：

1. 灰度百分位统计；
2. RGB 饱和度估算；
3. 动态亮度阈值；
4. 低饱和度亮区 mask；
5. 局部密度 box blur；
6. 逐行找左右边缘；
7. 逐列找上下边缘；
8. 鲁棒直线拟合；

### 鲁棒拟合

不要简单最小二乘一次完成。

```text

→ 解析求最大特征向量
→ 得到直线方向
```


建议上限：


## P0-3：所有检测器并行产生候选

创建 detector registry：

```ts
const detectors: CandidateDetector[] = [
  contrastLineDetector,
  maskLineDetector,
];
```

接口：

```ts
interface CandidateDetector {
  name: DetectionMethod;
  detect(
    features: ImageFeatures,
    options: DetectionSettings
  ): QuadCandidate[];
}
```

主流程：

```ts
function detectQuad(
  imageData: ImageData,
  settings: DetectionSettings
): DetectionResult {
  const features = buildImageFeatures(imageData);

  const candidates = detectors.flatMap((detector) =>
    detector.detect(features, settings)
  );

  const scored = candidates
    .map((candidate) => scoreCandidate(candidate, features, settings))
    .filter(isValidCandidate);

  const deduplicated = deduplicateCandidates(scored);
  const ranked = deduplicated.sort((a, b) => b.rawScore - a.rawScore);

  return finalizeResult(ranked, imageData);
}
```

### 候选去重

两个候选若满足任一条件，应视为重复：

```text
Quad IoU > 0.94
```

或者：

```text
四角归一化平均距离 < 0.012
```

重复时保留：

* 分数更高的；
* diagnostics 更完整的；
* 非 fallback 的。

## P0-4：支持两种边缘极性

当前算法只偏好：

```text
inside > outside
```

改成分别计算两套分数：

```ts
const positiveScore = scoreSignedContrast(diffs);
const negativeScore = scoreSignedContrast(diffs.map((v) => -v));
```

选择：

```ts
if (positiveScore >= negativeScore) {
  polarity = "inside-brighter";
  score = positiveScore;
} else {
  polarity = "inside-darker";
  score = negativeScore;
}
```

### 新的单边特征

每条边都需要记录：

```ts
type EdgeEvidence = {
  polarity: EdgePolarity;
  medianContrast: number;
  percentileContrast: number;
  supportRatio: number;
  continuity: number;
};
```

### 评分原则

不能直接使用：

```text
mean(abs(diff))
```

因为少量超强内部线条可能产生高分。

应该同时要求：

* 有足够比例的采样点支持同一极性；
* 支持点沿整条边分布；
* 不能只集中在一小段。

初步规则：

```text
supportRatio < 0.18
→ 该边无效

最大连续支持长度 < 边长的 12%
→ 降权

正负极性接近 50:50
→ 标记 mixed 并降权
```

## P0-5：统一候选评分

P0 阶段建议使用清晰、可解释的线性评分，不要立刻引入机器学习。

```text
score =
    0.30 × edgeStrength
  + 0.22 × edgeSupport
  + 0.16 × insideOutsideDifference
  + 0.12 × regionConsistency
  + 0.10 × geometryValidity
  + 0.07 × normalizedArea
  + 0.03 × sourceAspectPrior
```

注意：

```text
normalizedArea 权重从当前的强奖励降到较弱先验
```

避免整张照片边框天然获胜。

### Geometry validity

必须包含：

* 四边形凸；
* 无自交；
* 四个角不重复；
* 面积不低于图片 8%；
* 角点不能超出图片超过 20%；
* 最短边不能小于图片短边 10%；
* 相邻边夹角不能接近 0° 或 180°。

硬性失败直接丢弃，不只是降分。

### Region consistency

对候选四边形内部和外部建立低分辨率统计：

* 内部亮度方差；
* 内部颜色分布；
* 外部颜色分布；
* 内外 Lab 或 opponent-color 距离。

不要假设内部必须更亮。

## P1-2：实现 orientation-guided Probabilistic Hough

建议优先实现 Probabilistic Hough，而不是第一版就实现完整 LSD。

原因是：

* 更容易在 TypeScript 和 Python 保持一致；
* 可以直接利用已有梯度方向；
* 不必引入大型 OpenCV.js WASM；
* 可以控制 bundle 大小和浏览器兼容性。

创建：

```text
hough-lines.ts
hough_lines.py
```

### 边缘点筛选

只保留：

```text
gradient magnitude > 自适应阈值
```

建议阈值：

```text
第 82–88 百分位
```

同时设置最低阈值，避免低对比图像全部成为边缘。

### 方向约束投票

普通 Hough 会让每个点向大量角度投票，计算量较大。

使用梯度方向：

```text
候选线的法线方向
≈ 梯度方向
```

每个像素只向：

```text
gradientAngle ± 5°
```

范围投票。

### 提取线段

获得 Hough 峰值后：

1. 收集距离该直线小于 2–3 px 的支持点；
2. 把支持点投影到直线方向；
3. 按投影位置排序；
4. 当相邻点间距超过阈值时切断；
5. 得到一个或多个有限线段；
6. 过滤过短线段。

线段至少满足：

```text
长度 > 图片对角线的 10%
```

屏幕边缘候选可以稍微宽松：

```text
8%
```

## P1-3：去除固定方向和固定斜率限制

当前不能再预设：

```text
top 接近水平
left 接近垂直
```

### 方向聚类

对所有长线段方向使用：

```text
cos(2θ), sin(2θ)
```

进行聚类，因为：

```text
θ 和 θ + 180°
```

表示同一条无向直线。

目标是得到两个主要方向族：

```text
family A
family B
```

这两个方向不要求严格垂直，但应满足：

```text
夹角 35°–145°
```

过于接近平行的组合无效。

### 生成边对

对每个方向族：

1. 计算各线相对图像中心的有符号距离；
2. 一侧作为第一条边；
3. 另一侧作为对边；
4. 选择距离足够大的线对。

然后：

```text
family A pair × family B pair
→ 四边形候选
```

不再使用 top/bottom/left/right 固定搜索窗口。

最后根据角点位置排序为：

```text
TL, TR, BR, BL
```

## P1-4：加入连续边缘支持率

创建统一函数：

```ts
evaluateEdgeEvidence(
  line: Line,
  gradient: GradientMap,
  colorFeatures: ColorFeatures
): EdgeEvidence
```

### 沿边采样

每条边采样：

```text
96–192 个点
```

根据边长动态决定。

每个点在法线方向检查：

```text
-4 px 到 +4 px
```

范围，找最大梯度。

### 计算指标

```ts
type EdgeEvidence = {
  meanStrength: number;
  medianStrength: number;
  supportRatio: number;
  longestRunRatio: number;
  largestGapRatio: number;
  gradientAlignment: number;
  signedContrast: number;
};
```

### continuity

将每个采样点转成：

```text
supported / unsupported
```

计算：

* 支持点比例；
* 最大连续支持区间；
* 最大断裂区间；
* 支持点分布熵。

一个内部表格横线可能很强，但通常：

* 只支持候选四边形的一条边；
* 或者支持集中在局部；
* 或者不能形成四边一致的外部边界。

## P1-5：四边局部精修

初步四边形只用于初始化。

对每条边单独优化：

```text
角度：±3°
偏移：±12 px
```

分两阶段：

### 粗搜索

```text
角度步长 0.5°
偏移步长 2 px
```

### 细搜索

围绕最佳点：

```text
角度步长 0.1°
偏移步长 0.5 px
```

目标函数：

```text
edgeObjective =
    0.35 × edgeStrength
  + 0.30 × supportRatio
  + 0.20 × longestRunRatio
  + 0.10 × gradientAlignment
  + 0.05 × signedContrast
```

优化四条边后：

1. 重新求四个交点；
2. 重新检查凸性；
3. 重新计算总评分；
4. 如果精修后分数下降或几何失效，则保留精修前结果。

### 精修限制

角点移动不能无限制：

```text
每个角点最大移动距离
≤ 图片对角线的 4%
```

否则容易跳到内部图表线。

## P1-6：使用第一名与第二名差距计算 confidence

先不要把原始评分直接当 confidence。

### 去重后取前两名

```ts
const best = ranked[0];
const second = ranked[1];
```

如果两者几乎相同但来自相同边界，只能在候选去重后比较。

### 基础特征

```text
bestNormalizedScore
scoreMargin = bestScore - secondBestScore
minimumEdgeSupport
minimumContinuity
geometryValidity
detectorAgreement
batchConsistency
```

### 初始规则

在没有足够标注数据前：

```text
confidence =
  0.30 × bestScore
+ 0.25 × scoreMargin
+ 0.20 × minimumEdgeSupport
+ 0.15 × detectorAgreement
+ 0.10 × geometryValidity
```

统一归一化到 `[0, 1]`。

### detector agreement

如果：

```text
contrast-lines
mask-lines
hough-lines
```

中至少两个方法给出 IoU > 0.9 的候选，可明显提高 confidence。

如果不同方法互相冲突，应降低 confidence。

### 自动 review 阈值

初始：

```text
confidence < 0.65
→ needsReview

best 与 second 的 Quad IoU < 0.75
且 scoreMargin 很小
→ ambiguous_candidates
```

真正阈值必须通过 benchmark 校准，不能凭感觉设完后不再调整。

---

## P1-7：利用同一批图片的几何一致性

这是整个 P1 中非常有价值的一步。

### 检测流程改成两遍

#### Pass 1：独立检测

所有图片分别运行完整检测器。

保存：

```ts
type PreliminaryResult = {
  imageId: string;
  normalizedQuad: Quad;
  confidence: number;
  method: string;
};
```

归一化坐标：

```text
x / imageWidth
y / imageHeight
```

#### Pass 2：建立批次几何先验

只使用：

```text
confidence ≥ 0.78
method !== fallback-frame
```

的图片。

根据归一化四角距离聚类。

简单距离：

```text
mean(
  distance(quadA[i], quadB[i])
)
```

聚类条件：

```text
distance < 0.045
```

每个 cluster 计算：

```text
四个角分别取中位数
```

得到 batch prior。

#### Pass 3：修复低置信度图片

对：

```text
confidence < 0.72
needsReview = true
```

的图片：

1. 将 batch prior 映射到当前图片尺寸；
2. 作为 `batch-prior` 候选；
3. 在其四条边附近执行局部精修；
4. 与原最佳候选重新比较。

### 防止错误传播

batch prior 只有在以下条件全部满足时才能使用：

* 至少 3 张高置信度图片；
* cluster 内归一化四角方差低；
* 当前图片尺寸方向一致；
* 当前图片上精修后的 edge support 达到最低要求；
* batch candidate 最终评分高于 fallback；
* batch candidate 不得仅因为接近 prior 就获胜。

`batchConsistency` 只能作为小权重先验，不能代替图像证据。

### 摄像机移动

同一批次可能中途移动手机，因此不能只计算一个全局中位数。

允许多个 cluster：

```text
camera-position-cluster-1
camera-position-cluster-2
...
```

低置信度图片分别尝试各 cluster prior，选择有最佳图像支持的结果。

# 六、网页 Worker 改造

当前 worker 是逐张检测并立即发送结果。

P1 后建议支持：

```ts
type WorkerMessage =
  | { type: "detect-start"; id: string }
  | { type: "detect-preliminary"; result: DetectionResult }
  | { type: "detect-final"; result: DetectionResult }
  | { type: "detect-batch-summary"; summary: BatchSummary }
  | ...
```

流程：

```text
解码图片
→ 独立检测
→ 发送 preliminary
→ 收集全部结果
→ 建立 batch prior
→ 对低置信度结果重新检测
→ 发送 final
```

UI 可以先展示 preliminary 结果，避免用户感觉页面卡住。

最终 PDF 必须只使用：

```text
detect-final
```

或用户手动修改后的 quad。

# 九、验收标准

## P0 完成标准

必须全部满足：

1. 输出页面比例切换不再改变检测坐标。
2. 网页端同时执行 contrast 和 mask 检测。
3. 暗色幻灯片＋亮背景能够使用反向极性。
4. fallback 页面全部带 `needsReview=true`。
5. UI 能显示待检查图片数量。
6. CLI 与网页端都输出候选和诊断字段。
7. 检测回归集进入 CI。
8. P0 的平均角点误差不得劣于 baseline 超过 5%。
9. 高置信度错误率不得上升。
10. 手动四角调整功能完全不受影响。

## P1 完成标准

1. 任意旋转角度不再受固定斜率范围限制。
2. Hough 候选和原检测器统一评分。
3. 强边但不连续的内部线条不能轻易获胜。
4. 局部精修在大部分正确候选上降低角点误差。
5. confidence 使用第一、第二候选差距。
6. 批次 prior 能修复部分单张失败，但不会覆盖强图像证据。
7. 四角全部低于 1% 对角线误差的比例明显提升。
8. `confidence ≥ 0.8` 的错误率低于设定阈值。
9. 桌面端 P95 检测耗时不超过 baseline 的 3 倍。
10. 移动端不会因内存峰值导致 worker 崩溃。

# 十一、Agent 必须遵守的约束

```text
1. 不得删除或弱化手动四角调整功能。
2. 不得把源图片上传到任何服务器。
3. 不得让输出页面比例进入边界检测评分。
4. 不得把 fallback-frame 标记成正常成功。
5. 不得只依赖单一 detector 的成功结果。
6. 不得使用面积作为主要评分项。
7. 不得只支持 inside-brighter 极性。
8. 不得在没有 benchmark 的情况下宣称准确率提升。
9. 不得一次性重写检测、渲染、PDF 和 UI 全部流程。
10. 每个 PR 必须包含测试和 benchmark diff。
11. 新算法失败时必须能够回退到上一稳定 detector。
12. diagnostics 必须足够详细，方便后续定位误识别原因。
13. 网页端和 CLI 的结果允许细微差异，但语义和字段必须一致。
14. 所有计算继续在本地浏览器或本地 CLI 内完成。
```

# 十二、建议 agent 首轮执行任务

第一轮只让 agent 完成以下内容：

```text
A. 建立检测 benchmark 和标注格式。
B. 将 slides-worker.ts 中的检测代码移入 detection/ 模块。
C. 定义 QuadCandidate、DetectionResult 和 needsReview。
D. 分离 sourceSlideRatio 与 outputPageRatio。
E. 保证切换 PDF 页面比例不会改变检测坐标。
F. 将 fallback-frame 标记为 needsReview。
G. 保持现有 contrast-lines 算法行为基本不变。
H. 添加相应网页端和 Python 测试。
```

不要让第一轮同时实现 mask、Hough、局部精修和 batch prior。

第一轮完成并验证无回归后，再按顺序执行：

```text
mask-lines
→ 双极性
→ 统一评分
→ 多尺度梯度
→ Hough
→ 连续性
→ 局部精修
→ confidence
→ batch prior
```

这种顺序能确保每一次准确率变化都可以明确归因，而不是最终得到一个难以调试的“大型新检测器”。
